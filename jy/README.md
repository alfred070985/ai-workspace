# 建议工作区（jy）

本目录用于收集各电脑、各工具提出的改进候选。核心原则是：**建议可以提交到独立分支，`main` 只能由默认整合者按每周归拢流程更新。**

## 角色

- **建议者**：任何加载本项目的工具或代理；负责发现共性问题、与用户沟通并形成候选。
- **默认整合者**：由用户指定的 Kimi 主会话；角色可以转移，但同一时间只有一个默认整合入口。
- **批准人**：用户；批准建议分支的提交与推送，以及每周 `main` 发布和已处理分支清理。

## 一条建议的提交规则

1. 建议者在对话中说明候选的来源场景、共性、适用范围和验证方法，不以单次偏好或偶然成功冒充普遍规律。
2. 用户确认时，必须明确是否授权“创建并推送本条建议分支”；没有该授权时只输出建议文本，不执行 Git 写操作。
3. 分支基于建议者可获得的 `main`，并在建议文件中如实记录 `base_commit`；无法确认是否为最新版本时明确标记，不擅自更新或声称最新。
4. 分支命名为：

   ```text
   jy/<tool>-<YYYYMMDD>-<short-slug>
   ```

   例如 `jy/workbuddy-20261126-recoverable-install`。名称冲突时增加简短唯一后缀，不覆盖、不复用、不强制推送。

5. 一条分支只新增一个建议文件，文件名与分支主体一致：

   ```text
   jy/<YYYYMMDD>-<tool>-<short-slug>.md
   ```

6. 使用 [`TEMPLATE.md`](./TEMPLATE.md)，不得修改 `thinking/`、`scripts/`、模板或其他文件；发现其他需要修改的内容时写入建议，不在本分支顺带实施。
7. 提交与推送仅限该 `jy/...` 分支，不直接提交或推送 `main`。建议被推送后仍是候选，不影响任何工具的正式协议。

## 每周归拢

默认整合者每周处理上一周的建议，本周新建议留到下一周期，避免一边审阅一边不断新增。具体时间或自动化由用户另行确认，本文件不创建定时任务。

整合流程：

1. 列出所有 `origin/jy/*` 分支，按 `base_commit`、来源工具和建议主题登记。
2. 阅读完整建议，合并重复项，识别冲突和过期假设；必要时向建议者或用户询问，不猜测。
3. 按接收、拒绝、暂缓分类，并说明理由。接收内容进入适当位置：核心原则、范式、可执行检查、技能或具体项目，而不是全部塞进 `CORE.md`。
4. 在 `jy/reviews/` 写入本周处理记录，保留建议来源、决定、验证证据和后续事项。
5. 向用户展示归拢清单、拟修改文件、验证结果和拟删除分支，取得一次每周总确认。
6. 经确认后提交并推送 `main`，再删除已经处理完成的本地与远程建议分支；未处理、暂缓或存在疑问的分支必须保留。
7. 拒绝或删除分支前，确保周记录已保留必要结论和原文依据；不得让“删除分支”变成无记录地丢弃经验。

## 安全边界

- 建议文件不得包含凭证、业务隐私、本机绝对路径或其他项目专有数据。
- 建议者不得因为拥有建议分支写权限，就推定自己拥有 `main`、工具配置或其他环境的修改权限。
- 分支冲突、身份异常、校验失败或远程访问失败时停止并报告，不擅自修复。
- 已处理分支删除属于 Git 写操作，必须包含在每周总确认中。
